## Summary

This phase is a consolidation exercise: two new components (`AppHeader`, `MinimalHeader`) are created, and five existing files are updated to use them. There are no new routes, no new API calls, and no new shadcn components to install — all required primitives (Avatar, DropdownMenu, Button) are already in `src/components/ui/`.

The primary technical consideration is the settings page conversion from client to server component. The settings page currently uses `authClient.useSession()` and `authClient.useActiveOrganization()` for session data — these hooks are client-only. Converting it to a server component means using `auth.api.getSession({ headers: await headers() })` (same pattern as the dashboard) and passing `userName` as a prop. The page's other client concerns (form state, dialogs, fetch calls) must remain in client sub-components or be handled differently.

The secondary concern is the DropdownMenu logout action in `AppHeader`. `AppHeader` must be a client component (it renders `DarkModeToggle` which uses `useTheme`), so inlining `authClient.signOut` via a dropdown item `onClick` handler is straightforward. The existing `LogoutButton` pattern (call `authClient.signOut()`, then `router.push("/sign-in")`) is the verified working pattern to replicate inside the dropdown.

**Primary recommendation:** Build `AppHeader` as a client component wrapping `DarkModeToggle`, Avatar, and DropdownMenu. Keep `MinimalHeader` as a thin client component wrapping `DarkModeToggle` only. Convert settings page to server component, extracting remaining client logic into a `HouseholdSettingsClient` sub-component.

### Pattern 1: AppHeader Component Shape

**What:** A client component accepting `userName: string` and `variant?: "default" | "settings"`. Renders a `<header>` with the shared shell, then conditionally renders the left zone and right zone based on variant.

**When to use:** On all authenticated app pages.

```tsx
// src/components/AppHeader.tsx
'use client'

interface AppHeaderProps {
  userName: string
  variant?: 'default' | 'settings'
}

export function AppHeader({ userName, variant = 'default' }: AppHeaderProps) {
  // Left zone: app name (default) OR back arrow + "Settings" label (settings)
  // Right zone: Avatar dropdown + [Settings icon if default] + DarkModeToggle
}
```

The component must be `'use client'` because it renders `DarkModeToggle` (which uses `useTheme`) and the DropdownMenu logout handler (which calls `authClient.signOut` and `useRouter`).

### Pattern 2: MinimalHeader Component Shape

**What:** A thin client component, DarkModeToggle only, full-width header shell.

**When to use:** Onboarding and auth pages.

```tsx
// src/components/MinimalHeader.tsx
'use client'

export function MinimalHeader() {
  return (
    <header className="border-b border-border bg-background px-4 flex items-center justify-end min-h-[52px]">
      <DarkModeToggle />
    </header>
  )
}
```

### Pattern 3: Settings Page Server Conversion

**What:** The settings page is currently a large client component (`"use client"`) using `authClient.useSession()` and `authClient.useActiveOrganization()`. Converting it to a server component requires splitting it.

**Approach:** Create a server shell (`page.tsx`) that fetches session + passes `userName` to `AppHeader`, then renders a client sub-component (`HouseholdSettingsClient.tsx`) for the interactive content (members, stores, dialogs). The client component continues to use `authClient.useActiveOrganization()` and `authClient.useSession()` for runtime data.

**Why splitting is necessary:** The page's interactive features (invite form, store CRUD, dialogs) are inherently client-side. Only the session fetch (for `userName`) needs server access. The server component does the session fetch; the client component does everything else.

```tsx
// src/app/(app)/household/settings/page.tsx  (NEW — server component)
import { auth } from '@/lib/auth'
import { headers } from 'next/headers'
import { redirect } from 'next/navigation'
import { AppHeader } from '@/components/AppHeader'
import { HouseholdSettingsClient } from './_components/HouseholdSettingsClient'

export default async function HouseholdSettingsPage() {
  const session = await auth.api.getSession({ headers: await headers() })
  if (!session) redirect('/sign-in')

  return (
    <div className="min-h-screen bg-background">
      <AppHeader variant="settings" userName={session.user.name} />
      <HouseholdSettingsClient />
    </div>
  )
}
```

The existing `page.tsx` body (minus the `<header>` block and floating DarkModeToggle) becomes `_components/HouseholdSettingsClient.tsx`.

### Pattern 4: Avatar Initials Helper

The settings page already has `getInitials(name: string)` — this same function is needed in AppHeader. Since both files will use it, inline it in `AppHeader.tsx` (it's 4 lines, no shared module needed).

### Pattern 5: DropdownMenu Logout Action

**What:** The avatar button triggers a DropdownMenu with a single "Log out" item. The item's click handler calls `authClient.signOut()` then navigates.

**Pattern from existing LogoutButton:**
```tsx
// Replicate this pattern inside AppHeader's dropdown item onClick
async function handleLogout() {
  await authClient.signOut()
  router.push('/sign-in')
  router.refresh()
}
```

This requires `useRouter` from `next/navigation` in AppHeader — consistent with `AppHeader` already being `'use client'`.

### Pattern 6: Icon Button with Link (Settings / Back Arrow)

**Established pattern in codebase:**
```tsx
<Button asChild variant="ghost" size="icon" className="min-h-[44px]">
  <Link href="/household/settings" aria-label="Settings">
    <Settings className="size-5" />
  </Link>

```

Back arrow in settings variant follows the same pattern with `href="/dashboard"` and `aria-label="Back to dashboard"`.

### Header Shell

Shared across all variants:
```tsx
<header className="border-b border-border bg-background px-4 flex items-center justify-between min-h-[52px]">
```

The 52px height is achieved via `min-h-[52px]` (same approach as `min-h-[44px]` on buttons — avoids fixed height issues with content overflow).

### Anti-Patterns to Avoid

- **Client-side session fetch inside AppHeader:** `AppHeader` must not call `authClient.useSession()`. Session is fetched server-side and passed as `userName` prop. This is a locked decision.
- **Duplicate DarkModeToggle:** After this phase, only `AppHeader` / `MinimalHeader` render `DarkModeToggle`. The ShoppingList controls bar toggle and floating fixed toggles must be removed.
- **Layout-level header injection:** Do not add header to `(app)/layout.tsx`. Per-page placement is the locked decision.
- **Three separate header components:** Use single `AppHeader` with variant prop, not three separate components. `MinimalHeader` is separate only because it has no auth context.
- **Hardcoded colors:** Use `bg-background`, `border-border`, `text-foreground`, `text-muted-foreground` semantic tokens only.

## Common Pitfalls

### Pitfall 1: Settings Page Conversion Breaks Client Hooks

**What goes wrong:** After converting settings `page.tsx` to a server component, leaving `authClient.useSession()` or `authClient.useActiveOrganization()` calls in the file causes a build error ("React hooks can only be used in client components").

**Why it happens:** These are React hooks — they only work inside `"use client"` components.

**How to avoid:** All hook calls stay in `HouseholdSettingsClient.tsx` (the extracted client sub-component). The server component `page.tsx` only calls `auth.api.getSession(...)` and passes `userName` to `AppHeader`.

**Warning signs:** Build error mentioning "useSession" or "useActiveOrganization" in a server component.

### Pitfall 2: DropdownMenu Portal and Dark Class

**What goes wrong:** The DropdownMenu renders via a Radix portal into `<body>`. If the `.dark` class is applied only to a subtree (not `<html>` or `<body>`), the dropdown loses theme styling.

**Why it happens:** Portaled elements are children of `<body>`, not the component tree. If `.dark` is only on a wrapper `<div>`, portal children won't inherit it.

**How to avoid:** Phase 4 used next-themes with `attribute="class"` on the `<html>` element — this means `.dark` is on `<html>`, which propagates to all portaled elements. Verify this works during implementation. (STATE.md notes this as a known concern to verify during Phase 4 verification.)

**Warning signs:** Dropdown menu renders in light mode while rest of page is dark.

### Pitfall 3: Removing DarkModeToggle from ShoppingList Breaks Layout

**What goes wrong:** The ShoppingList controls bar uses `DarkModeToggle` as a flex item at line 562. Removing it changes the flex layout — the controls row may need adjusting.

**Why it happens:** The toggle is currently a rightmost flex item in the controls row. Removing it leaves the row without that visual anchor.

**How to avoid:** After removing the import and JSX, verify the controls row still looks correct without the toggle. The toggle's width (ghost button ~32px + label) will no longer be reserving space.

**Warning signs:** Controls row elements shift or misalign after toggle removal.

### Pitfall 4: Auth Layout MinimalHeader Breaks Centering

**What goes wrong:** The auth layout currently uses `flex items-center justify-center` for full-viewport centering of auth forms. Adding a `<MinimalHeader />` above the content wrapper breaks the vertical centering (the header takes height, content is no longer centered).

**Why it happens:** The existing layout is a single flex column. Adding a header changes the layout model.

**How to avoid:** The auth layout needs restructuring when adding `MinimalHeader`. The header goes at the top; the remaining space uses flexbox to center the form content. Pattern:

```tsx
export default function AuthLayout({ children }: { children: React.ReactNode }) {
  return (
    <div className="min-h-screen flex flex-col bg-background">
      <MinimalHeader />
      <div className="flex-1 flex items-center justify-center px-4">
        <div className="w-full max-w-sm">{children}</div>
      </div>
    </div>
  )
}
```

**Warning signs:** Auth pages show form pinned to top instead of vertically centered.

### Pitfall 5: Onboarding Page Floating Toggle Removal Leaves Orphaned Import

**What goes wrong:** After removing `<div className="fixed top-4 right-4 z-50"><DarkModeToggle /></div>` from onboarding, the `DarkModeToggle` import remains, causing a lint error or unused import warning.

**How to avoid:** Remove the import line along with the JSX.
